# Domain Rules — Current Baseline v1.0

ฉบับรวมรอบ13. C-01–C-30และข้อเปิดอยู่ใน [PRD](01_PRD_REVIEW.md). D-01–D-25เป็นแนวทางออกแบบที่เลือก ไม่ใช่ผลplaytest; ไม่อนุญาตimplementation. เก็บตัวเลขและตัวอย่างที่ใช้อยู่ ตัดคำถามเก่าที่มีคำตอบแล้ว

## D-01–D-05 — แนวทาง MVP ที่เลือกตามการมอบหมายรอบ 6
สถานะ: ผู้ใช้มอบหมายให้เลือกแนวทางที่เหมาะสม จึงใช้เป็น baseline ออกแบบต่อได้ ไม่ใช่คำยืนยันสูตรเดิมจากผู้ใช้ ตัวเลขสมดุลปรับหลังทดลองได้ และยังไม่อนุญาต implementation

- D-01 Potential Type: เริ่ม Vitality (+HP), Might (+Attack), Guard (+Defense) ตัวละหนึ่ง Type กำหนดตาม Species ของลูก ไม่สุ่มหรือสืบทอด Type แยกใน MVP โบนัสเฉพาะค่านั้น = ค่าสถิติจาก Species/Level × (1 + 0.03 × ดาว); 0–5 ดาว เท่ากับ +0–15% ไม่เพิ่ม rarity/โอกาสสุ่ม/ความแรงสกิลโดยตรง สกิลอาจแรงขึ้นทางอ้อมผ่าน Attack; การปัดค่าสถิติตาม D-14
- D-02 รีเซ็ตดาว: เมื่อ rarity ลูกไม่ตรงกับตัวต้นทางทั้งสอง (เป็นระดับที่ไม่มีในคู่เดิม) ให้เริ่ม 0 ดาว ถ้าตรงกับตัวใดตัวหนึ่งให้ใช้การสืบทอดปกติ นิยามนี้ใช้กับทุกระดับที่ต่างใหม่ ไม่ได้บังคับว่าตารางผสมต้องอนุญาตผลระดับต่ำกว่าเดิม ตรวจรีเซ็ตก่อนคำนวณค่าเฉลี่ยและไม่สุ่มเพิ่มดาวในเส้นทางรีเซ็ต
- D-03 สืบทอดดาวปกติ: floor((ดาวตัวที่ 1 + ดาวตัวที่ 2)/2) แล้วมีโอกาสเพิ่ม 1 ดาว โดยผลไม่เกิน max(ดาวตัวต้นทาง) หรือ 5; ถ้าชนเพดานแล้วไม่สุ่มเพิ่ม ใช้ Level เฉลี่ยของทั้งสองกำหนดโอกาส p = min(0.03, 0.01 + 0.001 × (Level เฉลี่ย - 1)) โดย Level ต้องเป็นจำนวนเต็มตั้งแต่ 1 ขึ้นไป จึงเริ่ม 1%, เพิ่ม 0.1 percentage point ต่อ Level เฉลี่ย และสูงสุด 3% ที่ Level เฉลี่ย 21
- D-03a แหล่งดาว: ฝึกด้วยชัยชนะสะสมเฉพาะตัว ทุก 5 ชัยชนะเพิ่ม Potential 1 ดาวจนถึง 5 แยกจาก XP/Level เพื่อให้เส้นทางชัดเจน ตัวที่แพ้ไม่ได้ความคืบหน้านี้ เริ่มตัวจากไข่และตัวหลังผสมด้วยตัวนับชัยชนะ 0 ตัวจากไข่เริ่ม 0 ดาวทุก rarity ใน MVP ทำให้ตัวธรรมดายังฝึกถึง 5 ดาวได้; ตารางนี้เป็นค่าทดลอง ไม่ใช่เป้าหมายเวลาเล่นที่พิสูจน์แล้ว
- D-04 สกิล: ชุดสืบทอดรวม Inherited Skill และ Growth Skill ที่ปลดล็อกแล้วของตัวต้นทาง กรอง Compatibility และตัด Species Skill ออกก่อน รวมตาม skill ID ที่ไม่ซ้ำ น้ำหนัก 1 ถ้ามีในตัวต้นทางหนึ่งตัว และ 2 ถ้ามีในทั้งสอง สุ่ม 1 สกิล; นับการมีอยู่ต่อ Creature ไม่ใช่จำนวนช่อง ถ้าชุดว่างให้ผสมสำเร็จโดยช่อง Inherited ว่าง พร้อมบอกก่อนยืนยันผสม
- D-04a ช่องสกิล: Species Skill ของลูกกำหนดจาก Species; Growth Skill ของลูกกำหนดจากเส้นเติบโตของลูก หากสกิลสืบทอดตรงกับ Growth Skill ในอนาคตยังสืบทอดได้ แต่เมื่อปลดล็อกแล้วไม่สร้างโบนัสซ้อนหรือให้ใช้ซ้ำเป็นสองท่า แสดงเป็นสกิลเดียวที่มีสองที่มา ไม่สุ่มชดเชยใหม่ กฎนี้ลดข้อยกเว้นของ Compatibility และหลีกเลี่ยงความได้เปรียบจากช่องซ้ำ
- D-05 Level: ลูกเริ่ม Level 1, XP 0; Growth Skill ปลดล็อก Level 5 และสกิลนั้นยังล็อกจนถึงเกณฑ์ แม้ตัวต้นทางเคยปลดล็อกแล้ว ส่วน Inherited Skill ใช้ได้ทันที ช่วยเก็บคุณค่าจากพ่อแม่โดยยังมีเส้นทางฝึกตัวใหม่

### ตัวอย่างตรวจสูตร
- ดาว 2 + 4, Level 10 + 10, rarity ไม่รีเซ็ต: ได้ 3 ดาว และมีโอกาส 1.9% ได้ 4 ดาว
- ดาว 2 + 3: ปกติ 2 ดาว มีโอกาสได้ 3 ตาม Level; ดาว 3 + 3 ได้ 3 เสมอจากการผสม แต่ฝึกต่อถึง 4 ได้
- ลูกได้ rarity ระดับที่ไม่มีในคู่เดิม: เริ่ม 0 ดาว ไม่รับโบนัสสุ่มดาวรอบนั้น แต่ยังสืบทอดสกิลตาม Compatibility
- Skill A มีทั้งสองตัว และ Skill B มีตัวเดียว หลังกรองแล้วน้ำหนัก A:B = 2:1 จึงมีโอกาส 2/3 และ 1/3 ตามลำดับ
- World Condition เปลี่ยนได้เฉพาะ Weight Species/Element; ไม่มีตัวคูณเข้ากับสูตรข้างต้น แม้ลูกคนละ Species/Element อาจทำให้ชุดสกิลที่เข้ากันต่างกันทางอ้อม

### Trade-offs และเรื่องที่ยังค้าง
Level 1 และรีเซ็ตดาวทำให้ต้องฝึกใหม่ แลกกับการคุมพลัง ส่วนสกิลสืบทอดรักษาคุณค่าจากตัวเดิม ตัวเลขชัยชนะ/Level/โอกาสยังต้องทดสอบความรู้สึกว่าคุ้มและไม่ซ้ำซาก

สถานะข้อเปิดปัจจุบันดู O-01–O-05 ใน PRD; ห้ามใช้รายการค้างจากรอบเก่า

## D-06–D-10 — กติกาที่เลือกตามการมอบหมายรอบ 7
สถานะ: baseline สำหรับออกแบบต่อ ผู้ใช้มอบหมายให้เลือกแนวทางทั้ง 5 เรื่อง; ตัวเลขสมดุลเป็นค่าทดลอง ยังไม่อนุญาต implementation

### D-06 Rarity และขนาดคอนเทนต์
ใช้ Common → Uncommon → Rare → Epic ใน MVP ไม่มี Secret Character; rarity เป็นความหายาก ไม่ใช่ตัวคูณสถิติอัตโนมัติ

เพื่อรักษาขอบเขต C-10 ใช้ 8 Creature Definitions รวม variants ทั้งหมด ตาม D-12 ด้านล่าง: 2 Species × 4 rarity โดยสลับ Element ให้แต่ละ rarity มี Fire และ Water อย่างละตัว ตารางนี้แทนตัวอย่างจัดสรรรอบ 7 ที่บาง rarity มีเพียง Element เดียว จึงทดสอบ World Condition ได้โดยไม่เพิ่มจำนวนตัว

### D-07 Species และ Element
Species เดียวกันมีหลาย Element ได้ แต่แต่ละ Creature Definition ใน MVP มี Element เดียว ไม่ทำ Element ผสมหลายธาตุ

Species กำหนดรูปร่าง Species Skill และ Potential Type ส่วน Element กำหนด Compatibility และเป็นข้อมูลสำหรับ Controlled Random; ไม่เพิ่มระบบแพ้ทางธาตุโดยอัตโนมัติ MVP ไม่มี damage แพ้ทางธาตุตาม D-13

เพื่อไม่ให้กลุ่มผลว่างในชุด 8 แบบ เลือกใช้ Species/Element ของตัวต้นทางเป็นตัวปรับน้ำหนัก ไม่ใช่ข้อห้ามเด็ดขาดของผล Creature; กฎ Compatibility สกิลยังเป็นข้อห้ามตาม C-24 จากนั้นให้ World Condition ปรับน้ำหนัก Species/Element ภายใน rarity ที่ได้เท่านั้น ตัวคูณตาม D-20

### D-08 Base และ Jackpot
คู่ตัวต้นทางไม่สนลำดับ ตาราง Base แบบอนุรักษ์นิยมดังนี้:

| คู่ rarity | Base |
|---|---|
| Common + Common | Common |
| Common + Uncommon | Common |
| Common + Rare | Uncommon |
| Common + Epic | Uncommon |
| Uncommon + Uncommon | Uncommon |
| Uncommon + Rare | Uncommon |
| Uncommon + Epic | Rare |
| Rare + Rare | Rare |
| Rare + Epic | Rare |
| Epic + Epic | Epic |

หลักคิด: ใช้ลำดับ rarity 0–3 แล้วเฉลี่ยปัดลง กติกานี้เป็นการเลือกตารางของ MVP ไม่ใช่การตีความข้อยืนยันเดิมว่าต้องใช้สูตรนี้เสมอ ผู้เล่นเห็น Base และโอกาสแต่ละ rarity ก่อนผสม พร้อมแจ้งว่าตัวต้นทางหายและกรณีดาวรีเซ็ต

ตารางผล rarity ค่าทดลอง แยกจากน้ำหนัก Species/Element:

| Base | ผลปกติ | เพิ่มปกติ | Jackpot |
|---|---|---|---|
| Common | Common 90% | Uncommon 9% | Rare 1% |
| Uncommon | Uncommon 90% | Rare 9% | Epic 1% |
| Rare | Rare 90% | Epic 10% | ไม่มีระดับให้ข้ามเกินการเพิ่มปกติ |
| Epic | Epic 100% | ไม่มี | ไม่มี |

สุ่มจากหมวดที่ไม่ทับซ้อนกันหนึ่งครั้ง ไม่สุ่ม 9% และ 1% แบบอิสระ World Condition ไม่ปรับตารางนี้ จึงไม่เปลี่ยนโอกาส Jackpot; Base Rare รวมโอกาสขึ้นทั้งหมดเป็น Epic 10% และไม่เรียกผลนั้นว่า Jackpot ส่วน Base Epic ไม่รับรางวัลชดเชยที่ไม่ได้ตกลง

ความเสี่ยงที่ตั้งใจให้เห็น: Common + Epic มี Base Uncommon จึงอาจเสีย rarity สูง; ต้องแสดงผลลัพธ์/โอกาสและดาวรีเซ็ตให้ชัด ก่อนดำเนินการจริง

### D-09 การต่อสู้
MVP 1 ต่อ 1, turn-based/manual มีโจมตีพื้นฐานและสกิลที่ปลดล็อก ไม่มี mana โจมตีพื้นฐานใช้ได้เสมอเพื่อไม่ให้ติดสถานะทุกสกิล cooldown

กฎเดิมผู้เล่นเริ่มก่อนถูกแทนด้วย D-11: จัดลำดับตาม Speed ในแต่ละรอบ แต่ละฝั่งได้หนึ่งคำสั่งต่อรอบ สกิลใช้แล้ว cooldown 2 เทิร์นของเจ้าของ: ใช้ในเทิร์นส่วนตัว 1 จะใช้ซ้ำไม่ได้ใน 2/3 และกลับมาใช้ได้ใน 4 นับเฉพาะเทิร์นเจ้าของ ไม่รวมเทิร์นคู่ต่อสู้ ทุกสกิลเริ่มพร้อมใช้เมื่อต่อสู้เริ่ม และรีเซ็ต cooldown เมื่อเริ่มแมตช์ใหม่

แต่ละคำสั่งต้องแก้ผลเสร็จก่อนสลับฝั่ง HP ถึง 0 จบการต่อสู้ทันที ไม่ให้ฝ่ายแพ้ออกคำสั่งตอบโต้ กฎนี้ยังไม่รวม damage-over-time หรือผลตายพร้อมกันเพราะยังไม่เลือกสกิลเหล่านั้น ไม่ทำ timer บังคับเลือกในรุ่นทดลอง

### D-10 แพ้และรางวัล
แพ้ไม่ลบ Creature ไม่ลด Level/ดาว และไม่หักเงิน ใช้ตัวเดิมเริ่มแมตช์ใหม่ด้วย HP เต็มได้ การแพ้ไม่เพิ่ม XP/รางวัล/ชัยชนะ Potential เพื่อให้เส้นทางความก้าวหน้าชัด

ชนะให้ XP และรางวัลตาม D-16/D-17 ไม่ตีความว่าทุกชัยชนะต้องได้ไข่ เพิ่มตัวนับชัยชนะ Potential ตาม D-03a เพียงครั้งเดียวต่อแมตช์ วิธีป้องกันซ้ำและหลุดตาม D-23/D-24

### ตัวอย่างตรวจรับรอบ 7
- สลับตำแหน่ง Common/Epic ได้ Base Uncommon เหมือนเดิม; ผล rarity เป็น Uncommon/Rare/Epic ที่ 90/9/1
- Rare/Rare ให้ Rare 90% หรือ Epic 10% ไม่มี rarity นอกชุด
- Epic/Epic ได้ Epic เสมอ แต่ Species/Element/สกิลยังสุ่มตามกฎที่เกี่ยวข้อง
- World Condition เปลี่ยน น้ำหนัก Species/Element เปลี่ยนได้ แต่ตาราง rarity ข้างต้นต้องคงเดิม
- สกิลใช้เทิร์นส่วนตัว 1 ถูกปฏิเสธใน 2/3 ใช้ได้ใน 4; โจมตีพื้นฐานยังใช้ได้
- ผู้เล่นแพ้: Creature, Level, ดาวและเงินคงเดิม ไม่มีรางวัลเพิ่ม และเริ่มแมตช์ใหม่ HP เต็มได้

ข้อค้างก่อน T-03 เสร็จ: รายชื่อ/ผลสกิลและค่าสถิติจริง, XP/ราคา/อัตราไข่, Weight Species/Element/World Condition, จังหวะฟักและเกิดไข่, รูปลักษณ์เมื่อโต ส่วนบันทึก/หลุด/NFR ต้องปิดก่อน T-04

## C-27 / D-11 — Speed และลำดับเทิร์น รอบ 8
ยืนยัน C-27: ผู้ใช้ต้องการเพิ่ม Speed เป็นค่าสถิติในเกม turn-based

D-11 เป็นรายละเอียดที่เลือกสำหรับ MVP เพื่อให้ requirement ใช้งานได้ แทนกฎผู้เล่นเริ่มก่อนใน D-09:
- เพิ่ม Speed แยกจาก HP/Attack/Defense ใช้กำหนดลำดับออกคำสั่ง ไม่เพิ่ม damage หรือจำนวนเทิร์นโดยตรง
- เริ่มแต่ละรอบ เปรียบเทียบ Speed ปัจจุบัน ฝั่งสูงกว่าได้เทิร์นก่อน ฝั่งต่ำกว่าได้เทิร์นถัดไป แต่ละฝั่งมีหนึ่งคำสั่งต่อรอบหากแมตช์ยังไม่จบ
- Speed เท่ากัน: สุ่มอย่างเท่าเทียม 50/50 ในรอบแรก ถ้ายังเท่ากันในรอบต่อไปให้ฝั่งที่ได้ออกทีหลังในรอบก่อนเป็นฝ่ายเริ่ม เพื่อไม่ให้ฝั่งเดียวได้เริ่มตลอด ต้องเก็บลำดับรอบก่อน
- ตัดสินลำดับรอบจากฝั่งที่เชื่อถือได้ก่อนรับคำสั่ง ไม่ยอมให้ผู้เล่นส่งค่า Speed หรือเลือกว่าตนเองได้เริ่ม
- HP ถึง 0 จบแมตช์ทันทีตาม D-09 แม้อีกฝ่ายยังไม่ได้ใช้คำสั่งในรอบนั้น
- cooldown ยังนับเทิร์นส่วนตัวเหมือนเดิม ใช้เทิร์นส่วนตัว 1 พร้อมอีกครั้งที่ 4 การเป็นคนเริ่มรอบหรือการเสมอ Speed ไม่ลด cooldown เพิ่ม
- ไม่เพิ่ม extra turn, แถบสะสมเทิร์น, การหลบหลีกจาก Speed หรือสกิลเปลี่ยน Speed ใน MVP ครั้งนี้ หากเพิ่มผลเปลี่ยน Speed ภายหลังต้องออกแบบจังหวะคำนวณใหม่แยกต่างหาก
- Speed อิง Species/Level จากตารางสถิติที่จะกำหนด ไม่คูณ rarity โดยตรง ไม่มี Potential Type สำหรับ Speed เพิ่มโดยอัตโนมัติ D-01 ยังใช้ Vitality/Might/Guard เช่นเดิม

Trade-off: ใช้ Speed สร้างความต่างในการเริ่มโจมตี แต่ไม่ให้ตัวเร็วเล่นหลายครั้งต่อรอบ ระบบจึงอธิบายง่ายและรักษาบทบาทตัวช้าได้ ยังต้องทดลองค่าความแรงและ HP เพื่อไม่ให้ชนะด้วยโจมตีครั้งแรกเสมอ

ตัวอย่าง: Speed ผู้เล่น 12/มอนสเตอร์ 8 → ผู้เล่นเริ่มทุกครั้งที่ค่ายังเดิม; 8/12 → มอนสเตอร์เริ่ม; 10/10 → สุ่มผู้เริ่มรอบแรก แล้วสลับผู้เริ่มในรอบที่ยังเสมอ

## D-14 — สูตรสถิติและความเสียหาย
ค่า Level เป็นจำนวนเต็ม >= 1; Level cap10 และ XP curveตาม D-17

1. HP/ATK/DEF ก่อน Potential = baseStat × (1 + 0.08 × (Level - 1))
2. ค่าที่ตรง Potential Type คูณ (1 + 0.03 × stars) แล้ว floor ครั้งเดียว; ค่าที่ไม่ตรง Type floor หลังข้อ 1 ไม่ปัดกลางทาง
3. Speed = baseSpeed + (Level - 1) เป็นจำนวนเต็ม ไม่ได้รับ Potential bonus ใน catalog นี้
4. RawDamage = max(1, floor(SourceStat × SkillMultiplier × 100 / (100 + EffectiveTargetDEF)))
5. SourceStat ปกติคือ ATK สุดท้าย แต่ S02 ใช้ DEF สุดท้ายของผู้โจมตี; EffectiveTargetDEF คือ DEF สุดท้ายของเป้าหมาย ยกเว้น U01 ใช้ 0.5 × DEF โดยไม่ floor กลางทาง
6. ถ้ามี Shield: HPDamage = max(0, RawDamage - Shield) แล้วล้าง Shield; ถ้าไม่มี Shield HPDamage = RawDamage; HP ใหม่ = max(0, HP - HPDamage)

ไม่มี damage สุ่มใน MVP เพื่อให้การเลือกสกิลอธิบายผลได้ชัด rarity และ World Condition ไม่คูณ damage ไม่มี one-shot guarantee หรือการกล่าวอ้างว่าตัวเลขสมดุลแล้ว

Stat/Level/Potential ใช้ snapshot ตอนเริ่มแมตช์ ชัยชนะเพิ่ม XP/ดาวหลังจบจึงไม่เปลี่ยน Speed หรือ MaxHP กลางแมตช์ เริ่มแมตช์ใหม่ HP เต็ม สูตรนี้เพิ่มเป็น baseline ออกแบบ ไม่ใช่ระบบรักษานอกการต่อสู้

ข้อแลกเปลี่ยน: Defense ลด damage แบบอัตราส่วน ไม่ทำให้การโจมตีธรรมดาติดศูนย์จาก Defense อย่างเดียว แต่ค่าการเติบโต 8% และ scaling Defense ยังต้องลองที่ Level สูงหลังเลือก cap ไม่ใช้ตัวอย่าง Level 1 ยืนยันทั้งเกม

| 8 → 9 | 100 | 360 | 18 |
| 9 → 10 | 120 | 480 | 24 |

เลือกเก็บ totalXP ในช่วง 0–480 และ derive Level จากตาราง ไม่มี XP สะสมเกิน cap; ชนะที่ Level 10 ยังให้ Coin/โอกาสไข่/ชัยชนะ Potential ตามปกติ

Potential: เพิ่มดาวทุก 5 ชัยชนะใหม่จากฐานดาวที่ได้รับตอนเกิด/ผสม จึงคิดเป็น min(5, startingPotentialStars + floor(winsSinceCreation/5)) ไม่ใช้ floor(wins/5) เขียนทับดาวที่สืบทอดมา ตัวใหม่หลังผสมเริ่ม winsSinceCreation 0 เสมอ

ตัวจากไข่ 0 ดาวถึง 1 ดาวที่ชัยชนะ 5 และ 5 ดาวที่ชัยชนะ 25; ลูกที่สืบทอด 3 ดาวถึง 4 ดาวหลังชนะเพิ่ม 5 และ 5 ดาวหลังเพิ่ม 10 ครั้ง ทั้งหมดเป็น baseline เดิม D-03a ที่เขียนให้ตรวจได้ชัด

ผลจาก Level cap: สูตรโอกาสเพิ่มดาวเมื่อผสม D-03 ยังเหมือนเดิม แต่ MVP Level เฉลี่ยสูงสุด 10 จึงได้สูงสุด 1.9% ไม่ถึงเพดานสูตร 3% ห้ามแสดงโอกาส 3% เป็นค่าที่ทำได้ใน MVP นี้

ตรวจขอบเขตสถิติ Level 10: ตัวคูณ HP/ATK/DEF ก่อน Potential = 1.72; C01 0 ดาว = HP165/ATK48/DEF34/SPD25 และ 5 ดาว Might ATK55; C08 0 ดาว = HP189/ATK41/DEF58/SPD15 และ 5 ดาว Guard DEF67 ยังไม่มีข้อสรุปว่าสมดุลทุกคู่

## D-18 — สนามฝึกและตัวอย่างช่วงเริ่มเล่น
เพื่อไม่ให้เส้นทางฟรีขึ้นกับการชนะศัตรูยาก เลือกสนามฝึกเข้าถึงได้ตลอด: ใช้ C01 หรือ C02 เป็นศัตรู Level 1, 0 ดาว, HP เริ่ม 60% ของ MaxHP ปัดลง, ไม่มี Inherited และใช้ BASIC เท่านั้น Stat อื่นตาม catalog มีป้ายบอกว่าเป็นคู่ฝึก รางวัลตาม D-16 ไม่ต้องสร้าง Creature Definition ที่ 9

ข้อยกเว้นที่ระบุชัด: กฎเริ่ม HP เต็มใช้กับ Creature ผู้เล่นและแมตช์มาตรฐาน ศัตรูสนามฝึกมี HP เริ่มลดตามข้างต้น; ไม่แก้ค่า MaxHP จริง สนามมาตรฐาน/ระดับความยากเพิ่มเติมยังไม่ออกแบบในงานเศรษฐกิจนี้

ข้อแลกเปลี่ยน: สนามฝึกทำให้ farm ได้ง่าย ซึ่งยอมรับเพื่อพิสูจน์วงจรกับลูกใน MVP ส่วนการลดรางวัลศัตรูอ่อนหรือ progression gates ยังไม่เพิ่มก่อนมีผลทดลอง

### เส้นทางตัวอย่าง A: ลองผสมเร็ว
รับไข่ 1 + Coin20 → ฟัก → เก็บไข่จุดใกล้และฟัก → สู้ 1 ครั้ง → ถ้าชนะ Coin40, Creature ตัวที่สู้ Level2, ได้ไข่รางวัลแรก 1 → ผสมสองตัวเสีย Coin20 เหลือ Coin20 ได้ลูก 1 ตัว Level1 และยังมีไข่สำรอง

ทั้งสองตัวอาจยังไม่มีสกิลสืบทอด (Growth ล็อกก่อน Level5) ต้องบอกก่อนผสม ช่องว่างเป็นผลถูกต้อง ไม่แอบแจกสกิลนอกกฎ หากแพ้ Coin20 เดิมยังพอผสมครั้งแรกและเก็บไข่ต่อได้

### เส้นทางตัวอย่าง B: ลองสืบทอดสกิล
ฝึกตัวแรกให้ชนะ 4 ครั้ง → Level5 ปลดล็อก Universal Growth Skill → เก็บ/ฟักตัวที่สอง → ผสมได้สกิล Universal ของตัวแรกแน่นอน หากทั้งคู่ไม่มี Inherited และตัวที่สองยังไม่ปลดล็อก Growth

เงินหลัง 4 ชัยชนะ = 20 + 4×20 = 100; ผสม 1 ครั้งเหลือ 80 Coin ไม่ต้องซื้อไข่หากสำรวจ

### เวลาเป้าหมายและการตรวจความสนุก — ข้อเสนอรอทดลอง
สมมติแมตช์รวมเดิน/ตัดสินใจ 45–75 วินาที: ชนะ 4 ครั้งใช้เวลาสู้ 3–5 นาที รวมสอน/สำรวจตั้งเป้าเห็น Growth และลองผสมใน 8–12 นาที ไม่ได้บังคับผู้เล่นให้ผสมก่อนฝึก และไม่รับรองเวลาเมื่อมีการแพ้

ตั้งเป้าครั้งแรก 15–20 นาทีตาม P-03 เดิม: เห็นฟัก/สู้/ผสม และสังเกตอยากทำรอบใหม่หรือไม่ ไม่บังคับต้องได้ rarity สูงหรือ Jackpot

### ตรวจเศรษฐกิจและข้อจำกัด
- Coin จากชัยชนะหนึ่งครั้งจ่ายผสมได้หนึ่งครั้ง หรือสองชัยชนะซื้อไข่หนึ่งใบ
- หลังรางวัลแรก ไข่ต่อชัยชนะคาดหวัง 0.2 ใบ; 5 ชัยชนะคาดหวัง 1 ใบ ไม่ใช่รับประกัน
- จุดสำรวจ 3 จุด cooldown 90 วินาทีมีเพดานระยะยาว 2 ใบ/นาทีหลังรอบเก็บแรก หากเดินทันทุกจุด; ค่าจริงต่ำกว่านี้ได้ และเป็นทางแจกวัตถุดิบอย่างตั้งใจ
- ผสม Common/Common 10 ครั้งอิสระมีโอกาสอย่างน้อยหนึ่งผลเหนือ Common = 1 - 0.9^10 ≈ 65.13%; 34.87% ยังไม่ขึ้นเลย จึงไม่ใช้การขึ้น rarity เป็น acceptance ความสนุกช่วงสั้น
- ตัวเลขข้างต้นไม่จำลองการผสมต่อเป็น chain หรือรับประกันเวลาถึง Rare/Epic เป้าหมายนี้ต้องพิจารณาหลัง playtest

สถานะข้อเปิดปัจจุบันดู O-01–O-05 ใน PRD; ห้ามใช้รายการค้างจากรอบเก่า

## D-19 — World Condition v0.1 (รอบ 11)
สถานะ: baseline ออกแบบที่เลือกตามคำสั่งทำต่อ ตัวเลขเพื่อทดลอง ไม่ใช่ผล playtest ไม่มี implementation

แยกสภาพโลกเป็น timeOfDay (Day/Night) และ weather (Clear/Rain) จึงมี Day+Rain และ Night+Rain ได้ ไม่ถือว่า Rain แทน Day/Night

ใช้วงจรคงที่ 12 นาทีร่วมทุกเซิร์ฟเวอร์สำหรับ MVP จากเวลาฝั่งที่เชื่อถือได้และ epoch คงที่ของเกม ไม่เริ่มวงจรใหม่เมื่อผู้เล่นเข้า และไม่ทำวงจรส่วนตัว ไม่ต้องใช้บริการภายนอกเพิ่ม นิยาม phaseSeconds = (serverTime - configuredEpoch) modulo 720 โดยใช้ช่วงครึ่งเปิดดังตาราง

| phaseSeconds | สภาพโลก | ระยะเวลา |
|---|---|---|
| 0 <= t < 240 | Day + Clear | 4 นาที |
| 240 <= t < 360 | Day + Rain | 2 นาที |
| 360 <= t < 600 | Night + Clear | 4 นาที |
| 600 <= t < 720 | Night + Rain | 2 นาที |

Day/Night อย่างละ6นาที ฝนรวม4นาทีต่อวงจร ที่360เปลี่ยนเป็น Night+Clear, ที่720กลับ0 UI แสดงสภาพปัจจุบัน เวลาเหลือก่อนเปลี่ยน และคำอธิบายกลุ่มที่ได้ Weight เพิ่ม ไม่ให้ผู้เล่นเลือกเวลาเริ่มวงจรเอง ค่า configuredEpoch จริงเป็นค่าตั้งระบบก่อน implementation ไม่เปลี่ยนกลางรอบโดยไม่มี rules version

ข้อแลกเปลี่ยน: วงจรคงที่เดาง่ายและทดสอบซ้ำได้ แต่ตื่นเต้นน้อยกว่าฝนสุ่ม ยอมรับในรุ่นทดลอง ไม่มี event festival/ตารางเทศกาล/การเปิด event จากผู้ดูแลในงานนี้

## D-20 — Controlled Random weights v0.1
ลำดับ: ใช้ D-08 สุ่ม rarity ก่อน → เลือก Creature Definition เฉพาะ rarity นั้น → คำนวณน้ำหนักจากตัวต้นทางและสภาพโลก → normalize → สุ่มหนึ่งตัว → ประเมิน Potential/สกิลตามกฎเดิม

สำหรับ candidate แต่ละตัว กำหนด:
- baseWeight = 1 ทุก definition ใน catalog v0.1
- parentSpeciesFactor = 1 + จำนวนตัวต้นทางที่ Species ตรง candidate (ได้1/2/3)
- parentElementFactor = 1 + จำนวนตัวต้นทางที่ Element ตรง candidate (ได้1/2/3)
- timeFactor: Day ให้ Foxling 1.5, Shellkin 1; Night ให้ Foxling 1, Shellkin 1.5
- weatherFactor: Clear ทุก Element 1; Rain ให้ Water 2, Fire 1
- weight = baseWeight × parentSpeciesFactor × parentElementFactor × timeFactor × weatherFactor
- P(candidate | rarity, world, parents) = weight / ผลรวมน้ำหนักของ candidate ใน rarity นั้น
- P(candidate ทั้งหมด) = P(rarity ตาม D-08) × P(candidate | rarity, world, parents)

นับตัวต้นทางคนละ instance สองตัว ไม่สนลำดับการใส่ Species/Element ที่ไม่ตรงยังมีน้ำหนักบวกเสมอ Rain ทำให้ Water มากขึ้นและสัดส่วน Fire ลดลงผ่าน normalization ไม่ได้ปิด Fire

normalize ภายใน rarity เท่านั้น ห้ามรวมทุก rarity ก่อน normalize เพราะจะทำให้สภาพโลกเปลี่ยนโอกาส Jackpot ไม่ใช้ระดับ/ดาว/สกิล/เงิน/จำนวนครั้งที่เคยผสมเป็น Weight โดยอัตโนมัติ

ทุกคู่ rarity มีผลครบตาม catalog D-12 และทุก factor บวก ผลรวมต้อง > 0; หาก config ผิด/กลุ่มว่าง/weight ไม่เป็นค่าบวก finite ให้ปฏิเสธก่อนใช้ทรัพยากร ไม่สุ่ม fallback ข้าม rarity เงียบ ๆ

Weight สกิลยังมาจาก D-04 ไม่ใช้ timeFactor/weatherFactor; World Condition เปลี่ยนตัวลูกและ Compatibility ที่ตามมาทางอ้อมได้ แต่หากตรึงลูกและตัวต้นทางเดิม ตาราง Skill/Potential ต้องไม่เปลี่ยน

## D-21 — Preview และจังหวะยึดสภาพโลก
หน้าผสมก่อนยืนยันแสดงตัวที่จะเสีย, Coin20, Base, โอกาสแต่ละ rarity และรายชื่อ/โอกาส Creature ที่เป็นไปได้ พร้อมสถานะ Potential reset/ช่วงดาว และสกิลที่เข้ากันได้ของผลลูกแต่ละตัว ผู้เล่นยังไม่รู้ผลที่จะออกจริง แม้เห็นรายชื่อผลที่เป็นไปได้ ไม่เปลี่ยนเป็นการซ่อนโอกาส

- ถ้า phase/rules หรือข้อมูลตัวต้นทางเปลี่ยน: ไม่หัก Coin/ไม่ใช้ Creature/ไม่สุ่มผล ให้ refresh preview พร้อมแจ้งว่าข้อมูลเปลี่ยนและให้ผู้เล่นกดยืนยันในเกมใหม่ ไม่ใช้ผลเดิมหรือแอบเปลี่ยนโอกาส

## D-23 — Persistence baseline (รอบ 12, 2026-09-11)
สถานะ: แนวทางออกแบบที่เลือกเพื่อให้ระบบครบก่อน implementation; C-28–C-30ยืนยันdesktop1–4คน/หลุดยกเลิกแมตช์; NFRตัวเลขยังเป็นเป้าหมายเสนอและสเปกเครื่องจริงเป็นO-02

### รายการที่สำเร็จต้องคงอยู่
ผสม/ฟัก/ซื้อ/เก็บไข่/รับไข่ค้าง/รับรางวัล/ล็อกตัว รวม starter grant ต้องบันทึกก่อนตอบ committed. การฟัก3วินาทีเป็น presentation หลัง commit; หากต้องรอเซิร์ฟเวอร์นานกว่า3วินาทีให้แสดงกำลังบันทึก ไม่โชว์ผลสำเร็จล่วงหน้า

เลือกสองขั้นใน key เดียวสำหรับรายการที่มีผลสุ่มหรือเปลี่ยนทรัพยากร:
1. PREPARE: ตรวจ state/version/สิทธิ์/preview/world แล้วบันทึกแผนผลลัพธ์ immutable, operationId, sequence และ snapshot ของกฎ ยังไม่หักของหรือแสดงผลสุ่มให้ client. Durable PREPARED เป็นจุดยอมรับรายการ D-21; หลังจุดนี้เปลี่ยนโลกไม่ทำให้ stale
2. COMMIT: ตรวจ operation/fence แล้วใช้แผนเดิม หักทรัพยากรและให้ผลพร้อมกันใน UpdateAsync เดียว เพิ่ม lastAppliedSeq และเก็บ receipt แล้วล้าง prepared. หลังยืนยัน commit จึงแสดงผล/ใช้ลูก/ใช้รางวัล

รายการที่ถูกปฏิเสธก่อน PREPARE ไม่เปลี่ยนทรัพยากร. ไม่มี mutation อื่นแทรกระหว่างสองขั้น จึงคงเงื่อนไข capacity/ยอดเงิน. callback ของ UpdateAsync อาจถูกเรียกซ้ำ: ต้องไม่ yield, ไม่ส่ง network/UI และไม่สุ่มใหม่ใน callback ใช้แผนที่คำนวณครั้งเดียวก่อน callback พร้อมตรวจ expectedVersion/phase ภายในเพื่อปฏิเสธเมื่อ stale. prepared ที่พบอยู่มีสิทธิ์เหนือแผนที่กำลัง retry

ข้อแลกเปลี่ยน: อย่างน้อย2writesต่อ mutation มากกว่าบันทึกเป็นช่วง แต่เหมาะกับทดสอบเล็กที่ต้องรักษาผลสุ่มข้าม crash; ต้องวัดงบ request จริง ห้ามกล่าวว่ารองรับ scale โดยไม่ทดสอบ. ไม่บันทึกทุกเฟรมหรือทุกเทิร์นต่อสู้

### Retry และผลที่ยังไม่ทราบ
operationId ออกโดยเซิร์ฟเวอร์ ผูกกับผู้เล่น/session/ชนิดคำสั่ง/input fingerprint; ใช้ ID เดิมกับ input ต่างให้ปฏิเสธ. sequence เพิ่มใน profile ที่จุด PREPARE เท่านั้น. เก็บ receipt ล่าสุด100รายการและ lastAppliedSeq ถาวร; คำขอเก่าที่ receipt ถูกล้างให้ตอบ stale operation พร้อม refresh profile ไม่ตีความว่าเป็นรายการใหม่. ID ที่ไม่เคยออกใน session ปัจจุบันและไม่อยู่ใน prepared/receipt ใช้เริ่มงานใหม่ไม่ได้

timeout ไม่ได้แปลว่าไม่บันทึก: ยึดคิวผู้เล่นไว้แล้วตรวจ operation ใน key ด้วยการอ่าน/ตรวจจาก backend ที่ไม่ใช้ cache เก่า ก่อนตัดสิน retry. หากพบ prepared ให้ commit แผนเดิม หากพบ receipt คืนผลเดิม. หากผลยังไม่แน่ชัดคงสถานะ pending และไม่อนุญาตให้ส่ง ID ใหม่เพื่อทำรายการเดิมซ้ำ

retry ภายในใช้ backoff 1/2/4/8วินาทีพร้อม jitter และดูงบ request; หมดรอบแล้วแสดง pending/retry later ไม่บอก failed แล้วคืนของเดา ๆ ไม่ยิง retry ไม่จำกัด. recovery ต่อหลังโหลด profile หรือเมื่อ backend พร้อม

## D-24 — Session ownership และ recovery
ใช้ lease ใน key เดียว: sessionId, fencingGeneration, expiresAt. ค่าเริ่มทดสอบ TTL120วินาที ต่ออายุทุก30วินาทีหรือแนบกับ mutation; เซิร์ฟเวอร์ใหม่ acquire ผ่าน UpdateAsync เมื่อว่าง/หมดอายุ และเพิ่ม fencingGeneration. ทุก prepare/commit ตรวจ owner+generation+lease ยังมีผล เซิร์ฟเวอร์เก่าที่หมดสิทธิ์ห้ามเขียน แม้ callback/retry เดิมกลับมาภายหลัง

เมื่อ lease ต่อไม่ได้และหมดอายุให้หยุดรับ mutation; ถ้าอีก session ยังถือสิทธิ์ให้แจ้งรอและ retry ไม่ขโมย lease. บันทึก release เมื่อออกอย่างปกติเป็น best effort ไม่ใช่เงื่อนไขรับประกันเก็บข้อมูลทั้งหมด. หาก process ตายรอ lease หมดแล้ว recovery prepared ก่อนเปิดให้เล่น

เมื่อโหลดกลับ: acquire → validate schema → resolve prepared/receipt → แสดง profile ล่าสุด. สุ่มที่ยังไม่ถูก durable PREPARE ก่อน crash ไม่ใช่ผลที่สัญญากับผู้เล่นและไม่เคยเปิดเผย จึงไม่มีการรับประกันผลนั้น; หลัง PREPARE ต้องใช้ผลเดิมเสมอ. ไม่ restore snapshot เก่าทับ profile อัตโนมัติหากมี schema/dataผิดปกติ ให้หยุดและตรวจโดยผู้ดูแล

### แมตช์และการหลุด — C-30 ยืนยันแล้ว
ยืนยัน C-30: ไม่กู้แมตช์ที่ยังเล่นไม่จบหลังหลุด/เซิร์ฟเวอร์ดับ กลับมาเริ่มใหม่ ไม่มีเสียตัว/เงิน/Level/ดาว. ถ้าผลชนะ durable PREPARED แล้ว recovery จ่ายรางวัลเดิมครั้งเดียว; ถ้า crash ก่อน PREPARE รางวัลยังไม่รับประกัน จึง UI ต้องแสดงกำลังยืนยันผล ไม่ประกาศได้รับรางวัลสำเร็จ. การเลือกกลับมาต่อแมตช์เดิมจะเพิ่ม battle checkpoint และต้องทบทวน write budget ก่อน implementation

rewardId ผูก battleId ที่เซิร์ฟเวอร์สร้าง ไม่รับผลชนะ/จำนวนรางวัลจาก client. ห้ามเริ่มแมตช์ใหม่หรือผสมตัวเดิมระหว่างผลแมตช์อยู่ pending. HP/Shield/turn/cooldown เป็นสถานะแมตช์ใน memory ตาม C-30 ไม่ใช่ของใน inventory

### Fault cases ที่ต้องทดสอบก่อนปล่อย
- ก่อน prepare / หลัง prepare / หลัง commit แต่ก่อนตอบ / reconnect / ผู้ถือ leaseเก่ากลับมาเขียน / requestIdซ้ำหรือเปลี่ยนpayload
- ผสมจาก Coin20/ตัว2: สุดท้ายเป็นก่อนรายการ หรือ committed Coin0/ลูก1 เท่านั้น; prepared เป็นช่วงรอที่ยังมีของเดิมแต่ใช้ทำรายการอื่นไม่ได้
- รางวัลเริ่มต้น/รางวัลชัยชนะแรก/ไข่ค้างรับ ใช้ grant flags และ receipt ใน key เดียว ไม่จ่ายซ้ำ
- backend error ต้องไม่สร้างผู้เล่นใหม่ ไม่ reset node cooldown และไม่ล้างล็อกตัวโปรด

## D-25 — Validation และสภาพแวดล้อมทดสอบ
server ตรวจ identity จากการเชื่อมต่อ, ownership, instanceIdไม่ซ้ำ, schema/type/finite numbers/ขนาดข้อความ, Coin/capacity/level/cooldown/phase และระยะเก็บไข่. ไม่เชื่อ damage/result/clock/world ที่ client ส่ง

baseline rate limit ต่อผู้เล่น: mutation1รายการ in flight, เริ่มได้ไม่เกิน1ต่อวินาที burst2; previewไม่เกิน2ต่อวินาที burst4; battle actionไม่เกิน2ต่อวินาที burst2 พร้อมตรวจ turn revision; statusไม่เกิน1ต่อวินาที burst2. จำกัด payload request8KiBและ identifier128ตัวอักษร. ต้องใช้ token bucket ฝั่ง server และ rejected request ไม่เขียน DataStore. นี่เป็นค่า app ที่เสนอ ไม่ใช่ quota Roblox

แยก test experience/DataStore ออกจากข้อมูลเล่นจริง ไม่ทดสอบ migration/fault กับ profileจริง. เพิ่ม schemaVersion และ migration ที่ทดสอบกับสำเนา; log เฉพาะ operationId/rulesVersion/state/error/timing ไม่ dump profileเต็ม ไม่เพิ่มเครื่องมือส่งออกข้อมูลส่วนตัวใน MVP

อ้างอิงตรวจวันที่2026-09-11: [Roblox Data stores](https://create.roblox.com/docs/cloud-services/data-stores), [GlobalDataStore](https://create.roblox.com/docs/reference/engine/classes/GlobalDataStore), [Client-server boundary](https://create.roblox.com/docs/scripting/security/client-server-boundary). เอกสารยืนยัน API/ข้อจำกัด callback/validation ส่วน lease, receipts, จังหวะบันทึก และ SLA เป็นการออกแบบของโปรเจกต์ ไม่ใช่บริการรับประกันจาก Roblox
